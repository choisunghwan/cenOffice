# 코드 리뷰

## 언제 쓰나요
- 머지 요청(PR) 전에 변경 내용을 한 번 더 확인하고 싶을 때
- 다른 사람이 짠 코드를 검토하는데 놓친 부분이 없는지 보고 싶을 때

## 입력
- `git diff` 결과, 또는 파일 내용(파일 이름과 함께 붙이면 좋습니다)
- 선택: 언어·프레임워크, 이 변경의 목적 한 줄

## 진행 방법
1. 입력이 diff 이면 추가·변경된 줄(+)을 중심으로 보고, 주변 맥락은 필요한 만큼만 참고한다.
2. 아래 순서로 실제로 문제가 될 수 있는 것만 찾는다.
   - 정확성: null·빈 값 처리(NPE), 경계값·off-by-one, 예외 삼킴, 잘못된 조건, 자원 미반납
   - 보안: SQL 인젝션(문자열로 쿼리 조립), XSS(검증 없이 HTML 출력), 경로 조작, 하드코딩된 비밀번호·키, 권한 확인 누락
   - 동시성: 공유 상태를 잠금 없이 수정, 스레드에 안전하지 않은 객체 공유, 경쟁 상태
   - 성능: 반복문 안의 DB·네트워크 호출(N+1), 불필요한 전체 조회, 큰 데이터 복사
   - 유지보수: 의도를 알기 어려운 이름, 중복, 테스트가 없는 분기(중요한 것만)
3. 찾은 문제마다 위치(파일·줄), 심각도(높음/중간/낮음), 무엇이 문제인지, 왜 문제인지, 고친 코드 예시를 적는다.
4. 확신이 없으면 단정하지 말고 "확인 필요"로 표시하고 무엇을 확인해야 하는지 적는다.

## 결과 형식
1. 한 줄 요약: 머지해도 되는지(그대로 / 고친 뒤 / 다시 검토 필요)와 가장 큰 문제 하나
2. 표: | 위치 | 심각도 | 문제 | 이유 | 고치는 방법 |
3. 고친 코드 예시(심각도 높음·중간만)
4. 잘된 점 1~2개

## 예시
입력: `String sql = "select * from users where id = " + id;` 가 추가된 diff
결과: 위치 UserDao.java:42 · 높음 · SQL 인젝션 · 입력값이 쿼리에 그대로 붙음 · PreparedStatement 의 ? 자리표시자로 바꾸기

## 주의할 점
- 실제 위험이 있는 것만 짚고, 취향 차이(따옴표, 줄바꿈 등)는 요청이 없으면 다루지 않는다.
- 줄 번호는 입력에 보이는 것만 쓰고, 보이지 않으면 함수 이름으로 위치를 적는다.
- 결과는 사람이 검토할 의견이다. 실행해 보지 않았으므로 최종 판단은 담당자가 한다.
- 코드에 비밀번호·키·개인정보가 보이면 결과에 그대로 옮기지 말고 "민감 정보 포함, 제거 필요"로만 알린다.
- 참고: 공개 프로젝트 Alibaba Open Code Review(Apache-2.0)의 점검 분류를 참고해 사내용으로 새로 썼다.
