# 최소 구현 모드

가장 좋은 코드는 쓰지 않은 코드다. 이 모드가 켜져 있는 동안, 코드를 쓰거나 고치기 전에 항상 아래 순서로 따진다.

## 켜고 끄기
- 켜기: `/cen-lean-mode` (강도를 함께 줄 수 있다: `/cen-lean-mode 가볍게`, `/cen-lean-mode 강하게`)
- 끄기: 사용자가 "최소 구현 모드 꺼", "보통 모드", "stop lean" 이라고 하면 바로 평소대로 돌아간다.
- 한 번 켜면 끌 때까지 이 대화의 모든 코딩 작업에 적용한다.

## 쓰기 전 점검 순서 (위에서 멈출 수 있으면 멈춘다)
1. 필요한가: 요청을 다시 읽고, 지금 꼭 필요한 것만 남긴다. "나중에 쓸지도 모르는" 옵션·설정·추상화·확장 지점은 만들지 않는다.
2. 이미 있는가: 이 저장소 안에 같은 일을 하는 함수·컴포넌트·유틸이 있는지 먼저 찾아 그대로 쓴다.
3. 표준 라이브러리로 되는가: 언어 기본 기능으로 되면 그것을 쓴다.
4. 플랫폼 기본 기능으로 되는가: 브라우저·프레임워크·데이터베이스가 이미 해 주는 일을 직접 구현하지 않는다.
5. 이미 설치된 의존성으로 되는가: 새 라이브러리를 추가하지 않는다. 꼭 필요하면 이유와 함께 먼저 묻는다.
6. 그래도 필요하면: 동작하는 가장 짧고 읽기 쉬운 코드를 쓴다.

## 쓰는 방식
- 변경 범위는 요청을 해결하는 데 필요한 파일과 줄로만 한정한다. 관련 없는 정리·이름 바꾸기·포맷 변경은 하지 않는다.
- 새 파일·새 계층·새 인터페이스보다 기존 파일에 몇 줄 더하는 쪽을 먼저 고른다.
- 방어 코드는 실제로 일어날 수 있는 경우만 다룬다. 일어날 수 없는 경우를 위한 검사·분기는 넣지 않는다.
- 주석은 "왜"가 코드로 드러나지 않을 때만 짧게 단다.
- 테스트는 바꾼 동작을 확인하는 만큼만 추가한다.

## 강도
- 가볍게: 위 점검을 하되, 사용자가 요청한 구조는 그대로 따른다. 더 줄일 수 있는 곳은 끝에 한 줄로 제안만 한다.
- 보통(기본): 점검 순서를 따르고, 필요 없는 부분은 만들지 않은 뒤 무엇을 뺐는지 알린다.
- 강하게: 요청 자체가 과하다고 보이면 코드를 쓰기 전에 더 작은 대안을 먼저 제안하고 확인을 받는다.

## 작업 끝에 알릴 것 (짧게)
- 쓰지 않기로 한 것과 그 이유 (예: "설정 옵션은 지금 쓰는 곳이 없어 만들지 않음")
- 새로 쓰는 대신 재사용한 것 (예: "기존 formatDate 사용")

## 하지 않는 것
- 보안·데이터 손실 방지·접근성처럼 빠지면 문제가 되는 것은 줄이지 않는다.
- 사용자가 명시적으로 요청한 기능을 임의로 빼지 않는다. 과하다고 보이면 빼기 전에 묻는다.
- 짧게 만들려고 읽기 어려운 코드(한 줄에 몰아넣기, 의미 없는 이름)를 쓰지 않는다.

## 웹에서 한 번 실행할 때
CEN HUB 웹에서 이 스킬에 요구사항·설계·코드를 넣으면, 위 점검 순서로 "만들지 않아도 되는 것 / 이미 있는 것으로 되는 것 / 줄일 수 있는 코드"를 표로 정리해 준다. 결과는 검토용 제안이다.

참고: 공개 프로젝트 Ponytail(DietrichGebert/ponytail)의 원칙을 참고해 사내용 한국어 지침으로 새로 썼다.
